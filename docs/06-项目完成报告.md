# 项目完成报告（第一阶段）

项目：基于 MongoDB 的问卷系统
技术栈：Flask 3 + MongoDB 7 + pymongo，Jinja2 页面 + 原生 JS
代码规模：应用代码约 3100 行（Python 约 1880 行，模板与前端约 1250 行），测试约 1500 行

## 1. 项目目标

按初始需求实现一个"问卷星"式的简化系统：注册用户创建问卷、通过链接分发、登录用户填写、
按回答跳转、自动统计。课程明确不要求复杂界面，所以界面只做到"清楚可用"，
把精力放在数据库设计、后端逻辑和可验证性上。

本阶段的成果同时是第二阶段的基础，因此设计时额外考虑了三件事：
数据结构要能扩展、跳转规则要以数据形式存在、旧回答不能因为改题而失效。

## 2. 系统设计

系统分四层：页面（Jinja2）→ 蓝图（auth / surveys / fill / stats）→ 纯逻辑（`app/logic.py`）
→ 数据访问（`app/db.py` + pymongo）。完整说明见 [01-系统设计.md](01-系统设计.md)。

最重要的一个决定是：**把校验与跳转做成不依赖 Flask 和 pymongo 的纯函数**。
这样做带来三个直接好处：

1. 可以用几十个毫秒级的单测覆盖所有边界，不需要起服务、不需要连库；
2. 页面、JSON 接口、测试三处调用同一份规则，不会出现"前端跳了、后端不认"；
3. 第二阶段改规则时，只要单测还绿，就说明旧行为没被破坏。

问卷状态只有 `draft / published / closed` 三个，截止时间是一条约束而不是状态。
填写流程是服务端驱动：前端每答一题请求一次，服务端算下一题；提交时从头重走路径。

### 2.5 统计导出

统计结果除了在页面上看，还可以导出成 Excel：整卷统计页和单题统计页各有一个按钮。导出的工作簿有两张表，
「问卷信息」记录标题、状态、时间、题目数与回答数，「统计汇总」按题列出选项、人数、占比与统计值。

实现上把工作簿组装写成纯函数（`app/export.py`），统计口径直接复用 `stats.question_stats`，
不另写一套算法——否则很容易出现"页面显示 66.7%、导出的表算成 65%"这种不一致。
占比在单元格里是数值加 `0.0%` 格式，导出后还能继续参与计算；表头冻结、可筛选，
打印时横向缩到一页宽，方便直接作为附件提交。

## 3. MongoDB 设计

四个集合：`users`、`surveys`、`questions`、`responses`。完整字段、索引、示例见
[02-数据库设计.md](02-数据库设计.md)。

核心取舍：

- **问卷与题目用引用，回答与答案用嵌入。** 题目要单独改、要被跳转引用，所以独立成集合；
  一次提交是一个整体，统计要整份读取，所以答案嵌在 `responses` 文档里，一次 `insertOne` 写完。
- **跳转规则是数据。** 存在 `questions.logic.jumps`，代码只负责解释 `{when, target}`，
  加新条件类型不用改表结构，更不用改业务分支。
- **`responses.path` 单独存。** 记录"实际走过哪些题"，用于统计作答率和分析跳转效果；
  这是 `answers` 里没有的信息（没答的题不会出现在 answers 里）。
- **数据库层兜底。** 四个集合都有 `$jsonSchema` 校验器，`status`、`type` 用 enum 锁死；
  即使绕过应用直接写库，非法数据也进不来。
- **七个索引**，其中 `responses` 上的 `survey_id + answers.question_id` 是多键索引，
  让"只统计回答过某题的人"不用全表扫描。

为什么不用关系型：题型异构、规则半结构化、一次提交要写多行——这三点会让关系模型出现大量 NULL 列、
JSON 字符串字段或额外 JOIN。详细对照见数据库设计文档第 5 节。同时报告里也写明了关系型更强的地方
（强事务、跨表约束），避免得出"MongoDB 全面更好"的错误结论。

## 4. 跳转设计

规则存在题目文档里：

```javascript
logic: {
  default_next: "next",
  jumps: [
    { when: { option: "A" },            target: "<题目 id>" },
    { when: { contains_any: ["B"] },    target: "end" },
    { when: { op: "gte", value: 60 },   target: "<题目 id>" }
  ]
}
```

运行时有两个函数：

- `next_question()`：填写过程中找"第一道还没答的题"，遇到就返回；
- `build_path()`：提交时从头走完整条路径，逐题校验，并检查用户提交的每个答案是否落在路径上。

第二个函数是防作弊的核心。举例：Q1 选 A 直接跳到 Q4，如果请求里多带了 Q2 的答案，
`build_path` 会发现 Q2 不在 `path` 中并拒绝整次提交。这条规则有专门的测试
（`test_submit_rejects_answer_for_skipped_question`）。

环路和悬空目标都有防护：运行时检测环路并报错，删除题目时主动清理指向它的跳转，双保险。
详细实现与边界清单见 [04-关键逻辑说明.md](04-关键逻辑说明.md)。

## 5. 校验设计

校验分两层：

- **单题**：`validate_answer` 按题型检查。单选查选项存在性；多选查未知选项、重复、数量上下限；
  文本查字数；数字查类型、整数、范围。空值统一判断，必答抛错，选答返回 `None`。
- **整卷**：`build_path` 在走路径时逐题调用单题校验，缺必答直接终止并定位到具体题目。

细节上处理了几个容易漏的点：`True` 不能当数字 1（先排除 bool）；`NaN/Infinity` 拒绝；
中文按字符数（不是字节）计算；数字字符串 `"18.5"` 在要求整数时直接拒绝，不做隐式取整。

前端也做了即时提示（必答、多选数量提示），但**前端提示只是体验，最终判定永远在服务端**。

执行 `pytest -q`：**122 passed**（约 15 秒），无失败、无跳过。
测试连的是真实 MongoDB 7.0.14（不是 mock），每个用例前清空数据，结束后删测试库。

覆盖面：账号与越权（10）、问卷与题目管理（19）、填写与跳转（15）、校验（22）、
统计聚合与页面（12）、统计导出（17）、数据库校验器与索引（10）、纯函数单测（31，含重叠计数）。

统计结果是逐项核对过的真实数值，例如单选题 3 份回答 A/A/B，断言为 A=2、B=1、C=0、A 占 66.7%，
而不是只检查页面能打开。

## 7. 遇到的问题与解决

### 7.1 多选题的跳转规则全部不生效

最初给多选题存的条件是 `{"option": "A"}`（照搬单选题），而 `match_condition` 对多选题只认
`contains_any / contains_all / count`，结果规则永远不命中，测试里表现为"跳转后到了下一题"。

修法：`_build_logic` 按题型生成不同条件——单选用 `option`，多选用 `contains_any: [key]`。
这个 bug 说明"界面看起来配置成功了"不等于"规则真的能匹配"，必须有用例断言跳转后的题目 id。

### 7.2 统计页渲染报 `TypeError: object of type 'builtin_function_or_method' has no len()`

模板里写 `{{ data.values|length }}`。`data` 是普通 dict，Jinja 的属性查找会先取到
`dict.values` 这个内置方法，而不是键 `"values"`。改成 `{{ data['values']|length }}`。

教训：Jinja 里对 dict 用点号访问，遇到 `items / keys / values / get` 这类名字会踩坑。

### 7.3 跑全量测试时 MongoDB 中途崩溃（Too many open files）

现象：单独跑每个测试文件都通过，一次跑全部时，跑到第 80 个左右开始 `ServerSelectionTimeoutError`，
mongod 日志里是 `WiredTiger panic ... __posix_directory_sync: Too many open files`。

原因：最初每个用例都 `drop_database` + 重新 `create_collection`（带校验器），
一百个用例反复建删集合，WiredTiger 的文件句柄没有及时释放，而运行环境的 `ulimit -n` 只有 1024。

修法：改成"整个测试会话建一次库，每个用例只清空文档，不删集合"。
集合、校验器、索引都保持不变，测试从 100 多秒降到 30 秒，也顺手解决了句柄耗尽。
这是典型的"测试写法影响被测系统稳定性"，不是业务代码的 bug。

### 7.4 MongoDB 在后台启动后，下一条命令就找不到进程

开发时用 `mongod --fork` 启动，结果下一条 shell 命令连接就失败。
排查发现运行沙箱会在每条命令结束时回收子进程，`--fork` 出来的进程也跟着退出。
修法：把"启动 mongod → 等待就绪 → 跑测试 → 关闭"写进同一个脚本，一次执行完。

### 7.5 其他小问题

- 新建问卷后测试拿不到记录：测试里注册后没有登录，创建请求被重定向到登录页。
  改成先 `login` 再建卷，并在 helper 里固定这个顺序。
- 模板里 `q.rules.min_choices is not none` 对缺失的键判断为真（Jinja 里 `Undefined` 不是 `None`），
  导致渲染出"至少 项"这种空话。改成 `q.rules.get('min_choices') is not none`。

## 8. AI 使用过程（摘要）

完整日志见 [07-AI使用日志.md](07-AI使用日志.md)。简要说明：

- **AI 帮了什么**：按需求生成四个集合的 schema 草案、跳转与校验引擎的骨架、Flask 路由与模板、
  测试用例清单，以及文档初稿。
- **AI 做错了什么**：多选题跳转条件用错（7.1）；模板里 dict 点号访问踩坑（7.2）；
  早期测试写法导致 MongoDB 句柄耗尽（7.3）；测试里漏了登录步骤（7.5）。
  这些都不是"语法错误"，而是设计判断上的偏差，必须靠实际运行与断言暴露。
- **我改了什么**：逐条核对字段与需求（例如匿名与限次的矛盾）、确认跳转语义（第一条命中即跳）、
  把"提交时重算路径"从可选项变成硬性要求、补充了删除题目时清理悬空跳转、调整了统计分母口径。
- **我设计了什么**：集合划分（引用 vs 嵌入的边界）、`path` 字段的必要性、
  服务端驱动的填写流程、两层校验的职责划分、以及第二阶段需要的兼容字段（`survey_version`）。

## 9. 已知限制

1. 匿名问卷无法按人限次（`respondent_id` 为 null），这是需求内部的矛盾，选择如实说明。
2. 已发布问卷改题会影响旧回答；删除题目后旧回答里的对应答案成为孤儿（统计不展示，但不清理）。
3. 选项用 A/B/C 自动编号，调整顺序会让旧跳转指向不同含义的选项，界面已提示。
4. 没有并发编辑的乐观锁，两个人同时改同一题会后写覆盖。
5. 前端未做自动化 UI 测试，只做了人工点击验证。

这些问题会在第二阶段结合新需求统一处理，而不是现在偷偷改掉。

- 数据结构：`survey_version` 已预留；`rules` / `logic` 是自由对象，加字段不需要迁移。
- 代码结构：规则集中在 `logic.py`，加题型或条件只需扩展两个函数，路由与模板改动很小。
- 测试：122 个用例是"旧功能仍可用"的基线，第二阶段每次改动后先跑一遍。
