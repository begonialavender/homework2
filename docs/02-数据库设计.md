# 数据库设计

数据库名：`survey_system`，四个集合：`users`、`surveys`、`questions`、`responses`。

先把结论放在前面：**用四个集合，不用一个大集合；问卷与题目用引用，回答与答案用嵌入；跳转规则作为文档内嵌数据存储，不落到代码里。**
下面逐条说明为什么。

## 1. 集合划分

| 集合 | 一条文档代表 | 增长方式 | 读写特征 |
| --- | --- | --- | --- |
| `users` | 一个账号 | 随注册量线性增长 | 按用户名点查，读多写少 |
| `surveys` | 一份问卷的元信息 | 随建卷量增长 | 列表按 owner 查，详情按 slug 查 |
| `questions` | 一道题（含选项、校验规则、跳转规则） | 随建题量增长 | 建卷时批量读，填写时逐题读 |
| `responses` | 一次完整提交（含路径与全部答案） | 随填写量增长，量级最大 | 只追加，统计时按 survey 聚合 |

**为什么不是"一个问卷一个大文档"**：如果把题目和回答都塞进 `surveys`，一份热门问卷会不断变大，
最终撞上 16 MB 的文档上限；而且每次提交都要改同一个文档，写热点集中在一处。
把增长最快的 `responses` 拆出去，是这套设计里最重要的一刀。

**为什么题目单独成集合，而不是嵌在 `surveys.questions` 数组里**：
题目需要被单独修改（改题干、调顺序、配跳转），如果嵌在问卷文档里，每次改一道题都要重写整个数组；
而且跳转规则要引用"跳到哪一题"，题目有稳定的 `_id` 才好引用。
代价是渲染时要多一次查询（`survey_id` 上建了索引，代价很小）。

## 2. 文档结构

### 2.1 users

```javascript
{
  _id: ObjectId("66f0c1a2b5e4d3c2a1f00001"),
  username: "alice",                       // 唯一索引
  password_hash: "scrypt:32768:8:1$...",   // 加盐哈希，绝不存明文
  created_at: ISODate("2026-10-17T08:00:00Z")
}
```

### 2.2 surveys

```javascript
{
  _id: ObjectId("66f0c1a2b5e4d3c2a1f00010"),
  slug: "kQ3vT9mZ",              // 分发链接用的短码，唯一索引
  owner_id: ObjectId("..."),     // 指向 users._id
  title: "课程反馈问卷",
  description: "大约 2 分钟",
  allow_anonymous: false,        // 是否记录填写者身份
  allow_multiple: true,          // 是否允许同一人多次填写
  status: "published",           // draft | published | closed
  deadline: ISODate(...) | null,
  created_at, published_at, closed_at,
  question_count: 4              // 冗余计数，只用于列表展示
}
```

`slug` 与 `_id` 并存是有意的：`_id` 是内部主键，`slug` 是给外部看的短码。
链接里暴露 `_id` 会泄露创建顺序等信息，短码还可以随时换（第二阶段如果要"重新生成链接"就不用动主键）。

### 2.3 questions

```javascript
{
  _id: ObjectId("66f0c1a2b5e4d3c2a1f00021"),
  survey_id: ObjectId("..."),    // 指向 surveys._id
  order: 0,                      // 从 0 开始，连续；上移/下移就是交换 order
  type: "multiple",              // single | multiple | text | number
  title: "你喜欢的水果",
  required: true,
  options: [                     // 单选/多选用；key 是提交时的值
    { key: "A", label: "苹果" },
    { key: "B", label: "香蕉" }
  ],
  rules: {                       // 按题型不同而不同，统一放在一个对象里
    min_choices: 2,
    max_choices: 3,
    // text:  { min_length, max_length }
    // number:{ min_value, max_value, integer }
  },
  logic: {
    default_next: "next",        // next | end
    jumps: [
      { when: { contains_any: ["A"] }, target: "66f0c1a2b5e4d3c2a1f00024" },
      { when: { contains_any: ["B"] }, target: "end" }
    ]
  }
}
```

`rules` 与 `logic` 都设计成"自由对象"：校验器只要求它是 object，不锁死具体字段。
这样加一种新校验（比如"必须是邮箱"）或新条件（比如"文本包含某关键词"）时，
不需要迁移数据，也不用改集合校验器。

### 2.4 responses

```javascript
{
  _id: ObjectId("66f0c1a2b5e4d3c2a1f00031"),
  survey_id: ObjectId("..."),
  respondent_id: ObjectId("...") | null,   // 匿名问卷为 null
  anonymous: false,
  submitted_at: ISODate("2026-10-17T09:12:33Z"),
  survey_version: 1,
  path: ["...q1", "...q4"],               // 实际走过的题目顺序
  answers: [                              // 只记录被回答的题
    { question_id: "...q1", value: "A" },
    { question_id: "...q4", value: "希望多办活动" }
  ]
}
```

三个关键决策：

1. **答案嵌入，而不是单独建 `answers` 集合**。一次提交天然是一个整体，统计时要按问卷取"一整份回答"，
   嵌入后一次查询就能拿到，写入是一次 `insertOne`（原子）。如果拆成 `answers` 集合，
   一次提交要写 N 条文档，要么用事务（MongoDB 单机没有副本集时不可用），要么承担部分写入的风险。
2. **`path` 单独存一份**。`answers` 只含有值的题，而"用户看到了哪些题"是另一回事：
   统计"这道题的作答率"、以及第二阶段分析跳转效果，都需要知道哪些题被展示过。
3. **`survey_version` 预留**。第二阶段需求变更后，新旧问卷结构可能不同，回答里带上版本号，
   统计时可以按版本分别处理，不必猜。

## 3. 索引

| 集合 | 索引 | 类型 | 服务的查询 |
| --- | --- | --- | --- |
| users | `username` | 唯一 | 登录、注册查重 |
| surveys | `slug` | 唯一 | 按链接打开问卷 |
| surveys | `owner_id + created_at -1` | 普通 | 我的问卷列表（按时间倒序） |
| questions | `survey_id + order` | 普通 | 按问卷取题并保持顺序 |
| responses | `survey_id + submitted_at -1` | 普通 | 统计与最近提交 |
| responses | `survey_id + respondent_id` | 普通 | 判断某人是否已提交 |
| responses | `survey_id + answers.question_id` | 多键索引 | 统计单题时过滤"答过这题的回答" |

最后一条是多键索引（multikey）：`answers` 是数组，MongoDB 会为每个元素建索引项。
它让"只取回答过第 3 题的文档"不必全表扫描，是统计性能的关键。

## 4. 数据库层校验：$jsonSchema

四个集合都通过 `collMod` 设置了 `validationLevel: "strict"`、`validationAction: "error"`。
也就是说，就算有人绕过 Flask 直接往数据库里写，非法数据也进不来：

- `status` 只能是 `draft / published / closed`；
- `type` 只能是四种题型；
- `responses` 必须有 `submitted_at`、`path`、`answers`；
- `surveys.slug` 长度 4~32，`title` 非空。

这是 MongoDB 相对"无 schema"刻板印象的一个实际用法：**结构灵活 ≠ 可以乱写**。
校验器管"形状"，业务规则（比如选项数量、跳转目标是否存在）仍然在 `logic.py` 里管，两层各司其职。

## 5. 为什么不用关系型数据库

把同样的需求放到 MySQL，大致会是这样：

```
users(id, username, password_hash, created_at)
surveys(id, owner_id, title, description, allow_anonymous, allow_multiple, status, deadline, ...)
questions(id, survey_id, order_no, type, title, required, ...)
options(id, question_id, key, label)                  -- 选项再拆一张表
rules(id, question_id, rule_type, value, ...)          -- 校验规则要么拆表要么塞 JSON 字符串
jumps(id, question_id, condition_type, condition_value, target_question_id)
responses(id, survey_id, respondent_id, submitted_at)
answers(id, response_id, question_id, option_id, text_value, number_value)  -- 又一张宽表
```

问题不在"能不能做"，而在三处摩擦：

1. **题型异构**。单选的值是选项 id，多选是多个选项，文本是字符串，数字是数值。
   落到关系表里要么建多列（`option_id / text_value / number_value` 大量为 NULL），要么建多张子表。
   MongoDB 里 `value` 一个字段就够，类型随题型变化，读取时不需要 JOIN 也不需要判空列。
2. **规则是半结构化数据**。跳转条件、校验规则在不同题型下字段完全不同。
   关系型里常见做法是存 JSON 字符串——那就等于"在关系库里用文档模型"，还失去了索引与校验。
3. **读取路径**。渲染一题要 options + rules + logic；提交一次回答要写 N 条 `answers`。
   MongoDB 里题目文档一次取完，回答一次写入。

需要说明的是：关系型数据库在**强事务、跨表约束、复杂报表**上仍然更强。
本项目没有跨文档事务需求（一次提交就是一份文档），也没有多表关联报表，
所以 MongoDB 的文档模型在这里是划算的，而不是"为了用而用"。

## 6. 为什么适合 MongoDB

- 文档结构与业务对象同构：一份问卷就是"元信息 + 题目列表 + 跳转规则"，读出来直接能渲染。
- 题型天然异构：`options`、`rules` 在不同题型下有不同字段，文档模型不需要为空字段留位。
- 写入模式是"一次提交 = 一次插入"，没有跨集合事务，单文档原子性足够。
- 统计是典型的聚合场景：`$unwind` 展开 `answers` 数组、`$group` 分组计数，一条管道解决。
- 第二阶段要加字段时，不需要 `ALTER TABLE`，也不需要给旧数据补列——旧文档缺字段就是缺字段，
  读取时按默认值处理即可。

## 7. 冗余与权衡（如实记录）

| 冗余项 | 为什么保留 | 风险与处理 |
| --- | --- | --- |
| `surveys.question_count` | 列表页避免每题都 `countDocuments` | 可能漂移；展示用，真实题数以 `questions` 为准 |
| `responses.answers[].question_id` 存字符串而非 ObjectId | 前端 JSON 里本来就是字符串，省一次转换；也便于和 `path` 对齐 | 占用略大；已在 `answers.question_id` 上建多键索引 |
| `responses.path` 与 `answers` 有重叠信息 | 统计作答率、分析跳转必须知道"展示过但没答"的题 | 增加少量存储；换来统计口径准确 |

明确不做的冗余：不在 `responses` 里冗余题干或选项文本。题干会改，冗余文本会和题目版本对不上，
统计时统一按 `question_id` 回查题目，宁可多一次查询也不制造不一致。

## 8. 已知限制（写进报告，不藏着）

1. **匿名 = 放弃按人限次**。`respondent_id` 为 null 时无法判断"同一个人"，所以匿名问卷实际允许多次提交。
   这是需求本身的内在矛盾（既要匿名又要防重复），选择如实说明而不是偷偷记录身份。
2. **改题影响旧回答**。已发布的问卷仍可编辑题目；如果删掉一道题，旧回答里对应的 `answers` 条目会成为孤儿。
   当前统计按题目回查，孤儿答案不会被展示，但也没有清理。第二阶段会正式处理"题目版本化"。
3. **选项顺序即选项 key**。选项用 A/B/C 自动编号，调整选项顺序会导致旧跳转指向新含义的选项。
   界面上已给出提示；更稳妥的做法是给选项独立 id，这是第二阶段可以做的改进。
4. **单机无副本集时没有多文档事务**。当前设计刻意把一次业务操作收敛到单文档写入，规避开这个限制。
