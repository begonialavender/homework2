# 第二阶段项目报告：题目库与版本化改造

> 在第一阶段「基于 MongoDB 的问卷系统」之上扩展，不改动原有功能，只按需求变更文档补齐八条新需求。

## 1. 需求理解：八条需求其实是三个机制

需求变更文档的八条要求，表面上是八个功能，实际可以归并成三个机制：

| 机制 | 对应需求 | 要解决的问题 |
| --- | --- | --- |
| 题目独立成实体 | 一、七 | 题目不再依附于某一份问卷，可以保存、归类、复用 |
| 版本化（只增不改） | 三、四、五 | 改题不影响旧问卷；历史可查；多版本并存 |
| 共享与跨问卷统计 | 二、六、八 | 题目可给别人用；能查到被谁用；能合并统计 |

第一阶段已经留好了两个口子：`questions` 是独立集合（题目本来就不在 survey 文档里）、`responses.survey_version` 预留了版本位。因此第二阶段不是推倒重做，而是把「题目」从「问卷的一部分」升级成「有身份、有历史、可共享的实体」。

关键判断是：**「修改题目不影响已发布问卷」不能靠约定，必须靠数据结构保证。** 如果问卷引用题库里的活文档，那么无论代码写得多小心，一次误操作就会改掉去年的问卷。所以采用「快照 + 冻结」：题目进入问卷时复制内容，问卷发布后快照不可变。

## 2. 总体设计

### 2.1 六个集合

第一阶段四个集合保持不变，新增两个：

- `banks`：题库（分组），一个用户可以建多个题库，题库可以共享；
- `question_bank`：题库里的**版本**，一条文档就是一个版本，写入后内容不再修改。

`questions` 的语义发生变化：它不再是「题目本身」，而是「问卷里的这道题」= 内容快照 + 问卷内编排（顺序、跳转规则）+ 溯源信息（来自哪条版本链、哪一版）。

`responses` 的每条答案多记两个字段：`lineage_id` 与 `version`。

### 2.2 版本链

```
lineage_id = Q3B59A492        ← 一条链共用，跨版本、跨问卷都不变
   ├─ v1  parent=null  root=v1
   ├─ v2  parent=v1    change_note="在问卷《人口统计》中修改"
   └─ v3  parent=v2    restored_from=v1   change_note="从 v1 恢复"
```

- `lineage_id`：稳定标识，跨问卷统计和「被谁使用」都认它；
- `version`：链内递增，`(lineage_id, version)` 上有唯一索引；
- `parent_id`：上一个版本，用来回答「现在这一版是从哪一版改来的」；
- `restored_from`：恢复操作专用，指向被恢复的那一版；
- 版本号分配 = 当前最大值 +1，撞号时（并发）由唯一索引拒绝后重算重试，最多 8 次。

**版本内容不可变**：应用层没有任何接口可以修改已写入版本的内容字段（type/title/options/rules/required），只有「生成新版本」和「恢复为新版本」两条路。

### 2.3 快照与冻结

题目进入问卷时，把选定版本的内容复制到 `questions` 文档，同时记录：

```
lineage_id, bank_version_id, version, snapshot_at, frozen
```

问卷发布时，该问卷所有题目置 `frozen=true`。之后：

- 编辑题目、加题、删题、调顺序一律拒绝（路由层判断 `survey.status != "draft"`）；
- 题库里生成新版本，不影响任何已发布的问卷（它们持有的是旧版本的副本）；
- 想改已发布的问卷，用「复制为新草稿」：新问卷是独立文档，题目快照复制过去，跳转目标重映射到新题目的 id，旧问卷与旧回答原样保留。

### 2.4 共享模型

题目版本带两个字段：`visibility`（private / shared）与 `shared_with`（用户 id 列表）。

- private：只有所有者可见；
- shared + 名单非空：名单内用户可见、可选用；
- shared + 名单为空：所有登录用户可见（公开题）。

共享设置针对整条链（`update_many` 更新该 lineage 的所有版本），因为用户心智里「这是同一道题」。

被共享的人可以基于这道题生成新版本（团队协作需要），但：

- 链的 `owner_id` 不变，新版本记录 `created_by`；
- 共享设置只有所有者能改；
- 生成的新版本属于同一条链，所有者的其他问卷不会被改动。

### 2.5 跨问卷统计

第一阶段统计按 `survey_id + question_id` 聚合，天然只能看一份问卷。第二阶段在提交时把 `lineage_id` 写进每条答案，于是跨问卷统计只需要一次聚合：

```javascript
{"$match": {"answers.lineage_id": "Q3B59A492"}},
{"$unwind": "$answers"},
{"$match": {"answers.lineage_id": "Q3B59A492"}},
{"$group": {"_id": {"survey": "$survey_id", "version": "$answers.version", "value": "$answers.value"},
            "count": {"$sum": 1}}}
```

同一道题的 v1 与 v2 会被合并；页面同时给出「按版本拆分」和「按问卷拆分」，让口径差异看得见。

## 3. 数据库设计

### 3.1 question_bank（版本）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `lineage_id` | string | 版本链标识，如 `Q3B59A492` |
| `version` | int | 链内递增，≥1 |
| `parent_id` / `root_id` | ObjectId / null | 上一版 / 链首 |
| `restored_from` | ObjectId / null | 恢复来源 |
| `change_note` | string / null | 版本说明，≤200 字 |
| `type` / `title` / `options` / `rules` / `required` | | 内容字段，写入后不可改 |
| `tags` | string[] | 标签，便于筛选 |
| `owner_id` / `created_by` | ObjectId | 链所有者 / 本版保存者 |
| `visibility` / `shared_with` | string / ObjectId[] | 共享范围 |
| `bank_ids` | ObjectId[] | 所属题库（多对多） |
| `archived` | bool | 预留归档位 |
| `created_at` | date | 本版创建时间 |

### 3.2 banks（题库）

`name`、`description`、`owner_id`、`visibility`、`shared_with`、`created_at`、`updated_at`。

解散题库只删除分组本身并把 `bank_ids` 里的引用移除，题目不受影响——这一点写在页面上，避免用户误以为「解散 = 删题」。

### 3.3 questions 的新增字段

| 字段 | 说明 |
| --- | --- |
| `lineage_id` | 来源版本链（迁移前的旧数据由脚本补齐） |
| `bank_version_id` | 快照对应的版本 `_id` |
| `version` | 快照的版本号 |
| `frozen` | 发布后置 true |
| `snapshot_at` | 快照时间 |

原有字段（`order`、`logic`）保留：顺序和跳转属于「这份问卷的编排」，不属于题目内容，因此不进版本。

### 3.4 responses 的答案结构

```
answers: [
  {question_id: "<问卷内题目 _id>", lineage_id: "Q3B59A492", version: 2, value: "B"}
]
```

`question_id` 保持一阶段的语义（统计单份问卷时仍用它），`lineage_id` 是新增的跨问卷聚合键。两个键都留在文档里，读旧代码和新统计都不需要迁移。

### 3.5 索引

新增：

| 集合 | 索引 | 用途 |
| --- | --- | --- |
| question_bank | `(lineage_id, version)` 唯一 | 版本号唯一，并发兜底 |
| question_bank | `(owner_id, created_at desc)` | 我的题目列表 |
| question_bank | `(bank_ids)` 多键 | 按题库筛选 |
| question_bank | `(visibility)` | 公开题筛选 |
| banks | `(owner_id, created_at desc)`、`(visibility, updated_at desc)` | 题库列表 |
| questions | `(lineage_id, survey_id)` | 使用情况、快照查找 |
| responses | `(answers.lineage_id)` 多键 | 跨问卷统计 |

### 3.6 校验器

六个集合都启用 `$jsonSchema`（`validationLevel: strict`）。新字段中：

- `question_bank` 的 `lineage_id`、`version`、`type`、`title`、`owner_id`、`visibility`、`created_at` 为必填；
- `questions.lineage_id`、`responses.answers.lineage_id` **刻意不设为必填**，否则第一阶段的历史数据无法通过校验；新写入由应用层保证一定有值，迁移脚本负责补齐旧数据。

## 4. 关键实现

### 4.1 建题即入库（需求一、七）

在问卷里新增题目时，先调用 `versioning.create_version()` 生成 v1，问卷文档再拿它的快照。因此「保存常用题目」不需要额外操作：所有题默认就在题库里，只是没放进任何分组。

`/bank/questions/new` 允许直接建题并指定题库、标签、版本说明。

### 4.2 改题即新版本（需求三、四、五）

草稿问卷里编辑题目时：

1. 解析表单得到新内容；
2. 若与原版本内容完全一致 → 不产生新版本（避免无意义的版本膨胀）；
3. 否则调用 `fork_version()` 生成 `v(max+1)`，`parent_id` 指向原版本（或该题当前引用的版本），`change_note` 默认「在问卷《…》中修改」；
4. 问卷快照改为指向新版本。

旧版本一字未动，因此：

- 其他问卷引用旧版本 → 不受影响；
- 同一道题的多个版本同时存在（需求五）；
- 版本历史里能看到 v1 → v2 → v3 的父子关系（需求四）。

题型不允许跨版本更改：题型是「这道题是什么」的身份，改题型应该新开一道题。`create_version` 会对比链首题型并拒绝。

### 4.3 发布冻结与复制（需求三）

发布时 `questions.update_many({survey_id}, {$set: {frozen: true}})`，路由层对所有结构变更做拦截：加题、改题、删题、调顺序一律返回提示并跳回。

已发布问卷要改，只能「复制为新草稿」：

- 新建 survey 文档（draft），复制设置；
- 逐题复制快照，保留 `lineage_id / bank_version_id / version`；
- 跳转规则里的目标 id 通过映射表重写到副本的题目 id，避免指向旧问卷；
- 原问卷、原回答完全不动。

### 4.4 版本恢复（需求四）

「恢复」不是把旧内容写回旧文档，而是以旧版本的内容生成一个新版本（`restored_from` 指向它，`parent_id` 指向当前最新版）。这样历史永远是一条只增的链，任何时候都能回答「谁在什么时候改成了什么」。

### 4.5 共享（需求二）

所有者可以设置共享名单或公开；被共享者能在自己的问卷里从题库选题、也能基于它生成新版本。可见性判断集中在 `versioning.visible_filter()`，列表页、选题页、详情页共用同一套规则，避免出现「列表看不到但直链能打开」的漏洞。

### 4.6 使用情况（需求六）

`versioning.usage()` 以 `questions.lineage_id` 聚合，再 `$lookup` 问卷、统计回答数，返回：问卷标题、所有者、状态、用到的版本、第几题、回答数。改题前先看这一页，就知道会影响到谁。

### 4.7 跨问卷统计（需求八）

`versioning.cross_survey_stats()` 按题型分别聚合：

- 单选 / 多选：按选项 key 合并计数，同时给出每个版本的分布。不同版本的选项标签可能不同，展示时以该版本自己的叫法为准；
- 数字：总体平均 / 最小 / 最大 / 样本数 + 按问卷拆分；
- 文本：按提交时间倒序列出，标注版本。

### 4.8 迁移（兼容第一阶段）

`migrate.py` 做三件事：

1. 给每道旧题建一个 v1 版本（所有者 = 问卷所有者，创建时间沿用问卷创建时间）；
2. 给 `questions` 补 `lineage_id / bank_version_id / version / frozen / snapshot_at`，已发布问卷的题置 `frozen=true`；
3. 扫描 `responses`，用 `question_id → (lineage, version)` 映射回填答案里的 `lineage_id / version`。

支持 `--dry-run` 预演，且幂等：已有的不重复处理，可反复执行。

迁移不会自动把「看起来相同」的旧题合并成一条链——无法可靠判断哪些是真重复，宁可让用户在题库里自己决定。

## 7. 演示流程（约 5 分钟）

1. 登录，点「题库 → 新建题目」，建一道「你的年龄是？」，放进题库「人口统计」；
2. 新建问卷 A，点「从题库选题」选用它，发布；填写两份回答；
3. 回到题库，对该题「生成 v2」，把题干改成「你的年龄段是？」；
4. 新建问卷 B，选 v2，发布并填写一份回答；
5. 打开「跨问卷统计」：能看到 A、B 合并后的分布，以及按版本、按问卷的拆分；
6. 打开问卷 A 的编辑页：题目显示「已冻结」，修改被拒绝；
7. 点「复制为新草稿」，在新草稿里改题、加题都正常，问卷 A 与它的回答原样不动；
8. 在题库里点「恢复为新版本」，选 v1，生成 v3，历史里同时看到 v1、v2、v3 与恢复来源。

## 8. 遇到的问题与解决

**版本号并发**：两个请求同时给同一道题建版本，会算出同一个版本号。先用唯一索引 `(lineage_id, version)` 兜底，捕获 `DuplicateKeyError` 后重算重试，最多 8 次。

**恢复的 parent 指向**：最初让新版本的 `parent_id` 指向被恢复的旧版本，结果版本链出现分叉，页面上「v1 → v2 → v3」的关系不再成立。改为 `parent_id` 指向当前最新版、`restored_from` 指向被恢复版本，既保持线性历史，又保留来源。

**无意义的新版本**：编辑题目但内容没变时也会生成新版本，版本号迅速膨胀。增加内容比较（题型、题干、选项、校验、必答五项），完全一致则不建版本。

**`answers.lineage_id` 与旧数据**：把该字段设为必填会让第一阶段数据无法通过校验。改为选填 + 应用层保证 + 迁移回填，并在报告中如实说明。

**跨版本选项合并**：v2 调整选项顺序后，A/B/C 的含义可能变化。统计页按「选项 key + 版本」分组，总体分布按 key 合并、标签以该版本的叫法为准，同时提供按版本拆分，避免把不同含义的 A 混在一起还不自知。

**已发布问卷的编辑入口**：服务端拦截后，前端也必须隐藏按钮，否则用户会反复点、反复被拒。模板里按 `frozen` 隐藏加题表单与增删按钮，只保留「查看」。

## 9. 已知限制（如实记录）

- 迁移无法自动识别「重复的旧题」，每条旧题独立成链，需要用户手动归并（当前未提供合并功能）；
- 版本链只支持线性追加与恢复，不支持显式的分支合并；
- 选项 key 在版本间可能重编号，跨版本统计按 key 合并，含义变化需要看「按版本拆分」；
- 跨问卷统计能看到所有使用该题的问卷，包括别人创建的；这是「题目所有者视角」，未做更细粒度的隐私控制；
- 题库解散不删题，但也不提供「彻底删除题目版本」的操作，历史数据一律保留；
- 题目冻结后无法解除，只能复制问卷；如需「撤回发布」，目前需要手工改库。

## 10. AI 使用说明

第二阶段同样使用 AI 辅助完成：需求拆解、集合与字段设计、聚合管道草稿、测试用例生成、文档撰写。人工负责：确定「快照 + 冻结」的总体策略、审查每次数据库变更、在真实 MongoDB 上跑全量测试、逐条核对需求与实现的对应关系。所有 AI 生成代码都经过测试验证后才保留。
